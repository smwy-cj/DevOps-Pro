## 四服务适配

旧入口仅支持根目录 main.c/helper.c，真实双方项目位于子目录，B06 仅有一个对象目标。此次四个角色复用既有 real_project.Project，传递同一份 project_config，按实际目标集合对比全量和增量结果。DRAFT 对实际子目录构建；MDFixer 生成带子目录的补丁并运行项目的构建、测试和头文件增量验证。

编排核对候选摘要、基线图和目标报告摘要、修复消费的报告摘要及任务标识。最终重检失败时恢复本次工作副本的 Makefile。输入仓库的提交和 Makefile 前后记录，原始项目不用于直接应用补丁。

运行环境为 GitHub Actions 的 Ubuntu Linux runner，四容器通过 HTTP 调用，共用一份教学镜像及工作目录。只有 DRAFT 挂载 Docker socket，四个服务端口仅监听 127.0.0.1。未将 CI 运行描述为在 47.110.130.56 的部署，也未声称四个独立镜像或 A06 远端服务已发布。

## 在 Linux Docker 主机复现

先检出候选标签或 Release 记录的完整 SHA，再在新的 checkout 中执行。Git 本地 user.name 使用本人的数字学号。需要 Docker 权限和固定镜像源的网络访问。

~~~bash
git config --local user.name 241880068
python3 run_e11e12.py build
python3 run_e11e12.py prepare
python3 labs/e13e14/prepare_release.py
export E14_ROOT="$PWD" E14_IMAGE=course-e11e12:241880068
export E14_UID="$(id -u)" E14_GID="$(id -g)"
export E14_DOCKER_GID="$(stat -c '%g' /var/run/docker.sock)"
docker compose -f labs/e13e14/compose.yaml -p e14-241880068 config --quiet
docker compose -f labs/e13e14/compose.yaml -p e14-241880068 up -d --wait
python3 labs/e13e14/run_release.py --image "$E14_IMAGE" --compose-project e14-241880068
docker compose -f labs/e13e14/compose.yaml -p e14-241880068 down
~~~

已有 data/e14-release 或 work/e14-release 时程序拒绝覆盖，应保留原件并使用新的 checkout。通过归档恢复镜像时，先 docker load -i runtime-images-linux-amd64.tar.gz，再将 image-inventory.json 中的 service_image 标记为对应的 E14_IMAGE 标签。实际项目候选镜像也在该镜像归档中，教师项目镜像仅记录 ID 和构建证据。
